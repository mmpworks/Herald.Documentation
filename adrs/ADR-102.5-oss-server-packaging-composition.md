# ADR-102.5 — OSS server packaging composition (four-package vs fat NuGet)

- **Status:** Proposed
- **Date:** 2026-05-18
- **Stage:** 2 (sub-ADR under ADR-102)
- **Mirrors:** umbrella `herald`

## Context

ServerOSS always self-hosts DashboardOSS from its own `wwwroot/`
(ADR-102). That decision raises a packaging question: how does the
SPA bundle get into `wwwroot/` at deploy time?

Two shapes work. They have different composability and different
install-time stories.

## Decision

### Pick the four-package shape

Four packages, with the customer install still one command:

- **`Herald.OSS`** — the kernel (today).
- **`Herald.DashboardOSS`** — the npm SPA source (Nancy's lane). Not a
  NuGet; this is the Vue/Vite source repo. Published to npm.
- **`Herald.DashboardOSS.AspNetCore`** — a NuGet package that carries
  the built SPA bundle and drops it into the consuming project's
  `wwwroot/` on build. Authored by the DashboardOSS release workflow;
  contains the artifact, not the source.
- **`Herald.ServerOSS`** — the server NuGet. PackageReferences
  `Herald.DashboardOSS.AspNetCore`. Configures `MapStaticAssets()`
  against the bundle path the asset package lays down.

Customer install stays one line:

```
dotnet add package Herald.ServerOSS
```

Transitive resolution pulls `Herald.DashboardOSS.AspNetCore`, which
delivers the bundle to `wwwroot/`. The customer doesn't think about
the asset package; it's a transitive dependency that does its job.

## Alternatives considered

### Option B — fat NuGet

Bake the kernel, the asset bundle, and the server into one
`Herald.ServerOSS` NuGet. Customer install is one line. Fewer moving
parts. Matches the OSS-is-dead-simple framing tighter.

**Rejected** because the asset package is a clean CUPID-Composable
reuse seam. A third party building their own ASP.NET app could host
the DashboardOSS SPA inside it by PackageReferencing
`Herald.DashboardOSS.AspNetCore` directly, without pulling ServerOSS.
The composability is real and inexpensive; the four-package shape
costs one extra csproj on our side and zero clicks on the customer
side.

### Option C — git submodule

Pull DashboardOSS as a git submodule into ServerOSS at build time,
build the SPA in CI, copy to `wwwroot/`. **Rejected.** Submodules
move the build complexity from "package consumer" to "ServerOSS
maintainer." The npm + NuGet path keeps the dashboard release on its
own cadence and reduces ServerOSS's build to "restore packages,
compile, publish."

## Consequences

**Positive.** One customer install command. A clean reuse seam for
third parties who want the OSS dashboard hosted inside their own
ASP.NET app. The DashboardOSS release cadence stays independent of
ServerOSS releases — paid customers benefit too because
Dashboard.Paid can pin a different version range than ServerOSS does.

**Negative.** One extra csproj (`Herald.DashboardOSS.AspNetCore`)
and one extra publish lane in the DashboardOSS release workflow. The
package needs a clear README explaining "what is this and why did
NuGet install it for me?" — the customer doesn't reach for it directly.
Heather owns the README.

## Quick picture

> Picture buying a desk that comes with a lamp. You could buy a
> bundle box that has the desk and the lamp shoved in together, or
> you could buy the desk and have the lamp delivered separately
> with the receipt noting "this was included with your desk."
> Same one-click order. The second path means someone else can
> also order the lamp by itself for a different room. The composability
> costs the warehouse nothing and gives them a new SKU to sell.

## Rationale tied to CUPID + DRY

This is a CUPID *Composable* call straight down the middle. The
asset package is a single-purpose thing (deliver a built SPA to
`wwwroot/`) that knows nothing about the kernel or the server. Any
ASP.NET application can compose against it. The fat-NuGet alternative
would have welded the asset bundle to the server, removing the
composition seam without removing any duplication.

The decision avoids a future DRY problem too. If we ever want to
publish a "lite ServerOSS" without the dashboard, the asset package
is already separated; no extraction work needed.
