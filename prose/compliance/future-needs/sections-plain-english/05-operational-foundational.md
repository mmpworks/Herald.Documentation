# Plain-English: §10.1–§10.18 — operational requirements (foundational)

§10 carries 71 operational subsections (§10.1 through §10.71). They split naturally into clusters by what they normate. This file covers the foundational cluster — the operational discipline every institution adopting the spec needs, regardless of which §10.x extensions they choose.

---

## §10.1 Key-fingerprint reconciliation (normative)

**What.** SOC engagement procedure P-6 reconciles institution-side IKM custody records against the per-event `key_fingerprint` values on the chain. A discrepancy surfaces a botched rotation, a registry-mapping error, or a post-hoc IKM substitution attempt.

**Why.** §7 step 8 catches fingerprint mismatches at chain-walk time. P-6 is the audit-side complement — periodic reconciliation that catches drift between the chain and the institution's KMS/HSM records before drift becomes an audit finding.

## §10.2 Operational events (normative)

**What.** A list of `audit.*`-namespace events the institution emits as part of operations: `master_key.generated`, `master_key.rotated`, `seal_job.completed`, `seal_job.failed`, `audit_file.truncation_detected`, `verifier.run_completed`, `connector.lag_observation`, `connector.outage`, `master.cross_region_replication_completed`, `chain.partition_ceremony_attended`, `chain.coverage_map_published`, `chain.entity_succession`, `chain.successor_attestation`, `master.policy_changed`, `consumer_index.attestation`, etc. Plus the §10.59 RMA family, §10.65.2 `audit.fleet.profile_updated`, §10.69 `audit.disclosure.*` family, §10.70 `audit.privileged_investigation_access`, §10.71 `audit.wire.*` and `audit.ach.*` families.

**Why.** Operational events are control-evidence — the SOC engagement reads them, the examiner reads them, the IR program reads them. Putting them on the chain means a regulator three years from now can reconstruct the institution's operational history without trusting institution-side ambient logs.

## §10.3 Append-only enforcement (normative)

**What.** The chain ledger MUST be append-only. Once a chain entry lands, it cannot be modified or deleted. The institution's storage layer enforces this at the storage primitive (immutable-bucket cloud storage, append-only WAL, ledger-database write-once mode).

**Why.** Without append-only enforcement, an insider with chain-write access could rewrite history. The cryptographic chain proves no events were modified after capture; the storage layer proves no events were *removed*. The two compose.

## §10.4 Time synchronization (normative)

**What.** Application hosts and ledger servers SHOULD be NTP-synchronized. The day-boundary semantics use the ledger's `received_at` timestamp as authoritative; application-host clock drift is reported as a clock-skew anomaly, not an integrity failure.

**Why.** Different clocks → different interpretations of "which day did this event belong to." NTP gives the chain a coherent time discipline.

## §10.5 HSM custody (normative)

**What.** The signing key MUST be held in a FIPS 140-2 Level 3 (or higher) HSM with non-extractable private key. AWS CloudHSM, Azure Managed HSM, Azure Key Vault Premium with HSM-protected key, Google Cloud HSM are all conformant. AWS KMS without CloudHSM backing (FIPS 140-2 Level 2) is NOT conformant.

The seal-job operator role is granted `sign` only; `extract`, `delete`, `import` MUST require separate authorization.

**Fault-injection attacks (informative).** FIA / DFA against FIPS 140-2 Level 3 devices are accepted residual risk. Institutions in nation-state-attacker threat models select FIPS 140-3 Level 4 or Common Criteria EAL5+ HSMs.

## §10.6 IKM minimum length + §10.6.1 IKM generation requirements (normative)

**What.** IKM MUST be at least 32 bytes (256 bits) of cryptographic entropy generated by a FIPS-validated CSPRNG (HSM internal RNG, OS-level CSPRNG like `/dev/urandom`, or dedicated CSPRNG hardware). Weak RNG sources (system time + hash, sequential identifiers, language-stdlib non-cryptographic RNGs) are non-conformant.

**Why.** A weak-RNG IKM defeats the entire chain — per-tenant session-key isolation, fingerprint offline-non-grindability, layered authentication of §1.4 all depend on IKM unpredictability. Length minimum closes the offline-fingerprint-brute-force attack class.

## §10.7 Software-key adapter exclusion in production (normative)

**What.** Software-key adapters (IKM as bytes in a config file or environment variable) MAY ship in development/test builds but MUST be unreachable in production deployments. Two patterns satisfy: compile-time exclusion (build-flag removes the adapter source from the production binary) or run-time refusal (production runtime asserts the adapter is unreachable and aborts startup if it is).

**Why.** A run-time-only flag protecting a software adapter is brittle — an attacker with environment-variable write access bypasses it. Compile-time exclusion is the strict pattern.

## §10.8 Constant-time comparison (normative)

**What.** Fingerprint compare and MAC compare MUST use constant-time primitives (Go's `crypto/subtle.ConstantTimeCompare`,.NET's `CryptographicOperations.FixedTimeEquals`, Python's `hmac.compare_digest`). Variable-time compare leaks bytes via timing.

## §10.9 IKM registry retention (normative)

**What.** The institution MUST retain the IKM-to-`key_version` mapping for the chain's full retention period. Retiring an IKM that's still referenced by chain entries makes those entries un-verifiable.

## §10.10 Rotation crossing the seal boundary (normative)

**What.** When IKM rotation happens mid-day, the day's seal aggregates events under both the prior and new key. `seal.key_versions` lists both. The rotation event itself is captured as `master_key.rotated` on the chain.

### §10.10.2 Within-day algorithm rotation (Pattern A + Pattern B)

Two patterns for crossing an algorithm rotation (e.g., Ed25519 → Ed25519+ML-DSA-65) within a single day:
- **Pattern A** — both algorithms co-sign the day's seal record. The seal carries `signatures` array with both entries.
- **Pattern B** — the day produces TWO seal records, partitioned by `received_at` window (`covers_received_at_min`, `covers_received_at_max`). One under the prior algorithm, one under the new.

Pattern A is preferred (preserves "one seal per day" invariant). Pattern B is conformant but introduces a transient operational complication.

**Pattern B + v1.0b composition** (added 2026-05-09): Pattern B has both v1.0a (12-line) and v1.0b (14-line) `sign_payload` forms. Verifier dispatches on `sign_payload_version`; institutions migrating from v1.0a to v1.0b under Pattern B operate v1.0b base for new seals while v1.0a Pattern B seals remain verifiable indefinitely.

## §10.11 Adverse-action notice translation (ECOA + state-insurance) + §10.11.1 + §10.11.2 (normative)

**What.** When a customer receives an adverse-action notice (ECOA — credit decline, FCRA — credit reporting, state-insurance — declination/non-renewal/rate-up), the chain captures the customer-language translation step. Plus §10.11.1 normates the underlying adverse-action reasons schema (`audit.ecoa.adverse_action.*`). Plus §10.11.2 normates the FCRA §611 reinvestigation timing chain (`audit.fcra.reinvestigation.*`).

**Why.** Without chained translations, a CFPB examiner's question "what did this consumer actually receive?" depends on the institution's translation worker logs, which retain shorter than the chain. With the chain, the full lifecycle (decision → translation → dispute → reinvestigation) is reproducible from the chain alone.

## §10.12 Verifier CLI exit-code contract (normative) — *foundational*

**What.** Closed enum: `0` (PASS or PASS-STRUCTURALLY), `1` (FAIL), `2` (structural / input error — verifier couldn't begin §7), `3` (configuration error). Plus §10.29 streaming-state codes 4-6. Plus the additional-verifications-discipline that prevents combinatorial blow-up. Plus the verdict-object trailing-line emission. Plus the anomaly-line shape convention. Plus the marker namespace convention. Plus the REQUIRED-with-soft-enforcement pattern (control-completeness anomalies under `Status: PASS` rather than FAIL). Plus the institution-named-extension cross-check inheritance discipline.

§10.12 is the **structural backbone** for verifier output across the spec. Every §10.x section that emits anomalies, markers, or exit-code dispatch refers back to §10.12.

## §10.13 Evidentiary artifacts (informative)

**What.** A retention checklist for institutions whose chains may enter litigation: SDK version manifest, source-code hash + build reproducibility evidence, HSM configuration history, daily seal-job logs, change-management records, verifier output for the period.

**Why.** FRE 901(b)(9) authentication of the process — the chain proves the result; these artifacts prove the process.

## §10.14 Trusted-time integration (informative + forward commitment)

**What.** RFC 3161 trusted-timestamp integration is RECOMMENDED for v1.0; a future v1.x extension MAY define a normative `audit.timestamp.rfc3161_token` attribute. The forward-commitment paragraph specifies that the v1.x extension MUST name pre-MAC vs post-MAC binding posture; mixing in the same chain is non-conformant.

## §10.15 Multi-region resilience (normative) — *substantive*

**What.** Two patterns for multi-region deployment: Pattern A (active-active with seal-region pinning, single seal region per tenant per `seal_date`) and Pattern B (per-region `tenant_id`). Mutually exclusive per tenant.

**Pattern A invariants 1-7:**
1. Per-event MAC is region-agnostic (same IKM, same session_key everywhere).
2. Run-locality (v1.0): a run starts and ends in the same region; SDK per-process region binding enforces.
3. Single seal region per tenant per `seal_date`.
4. Day-boundary at the seal region.
5. Replication-loss detection via per-region event-count reconciliation.
6. Seal-region failover discipline.
7. **Region-attribute presence (added 2026-05-09).** `ffiec.chain.region` REQUIRED on every chain entry under Pattern A; verifier emits `Pattern A declared but ffiec.chain.region absent at seq N` under `Status: PASS`.

## §10.16 SaaS-edge capture connectors (normative)

**What.** Connectors mirroring SaaS records (Salesforce, HubSpot, Dataverse) into the chain MUST publish quantified four-number lag bounds in CC8.1: median lag, 95th-percentile lag SLO, alerting threshold, connector-outage RTO. Plus the `audit.connector_source.*` attribute family. Plus the **stable run_id discipline** with restart-byte-identicality conformance property (added 2026-05-09).

**Why.** Without quantified bounds, "near real-time" in a runbook is unfalsifiable. Without stable `run_id` derivation, every connector restart fragments a source record's history across multiple runs.

## §10.17 HSM partition ceremony attestation (normative)

**What.** Institutions operating HSM partitions under dual-control or witnessed-control MUST emit `chain.partition_ceremony_attended` events for partition creation, partition wipe, IKM rotation, partition-PIN reset, controlling-person rotation. Schema includes signatories array (role + name + entity_affiliation) and witness, plus SHA-256 of the scanned attendance-log PDF.

**Why.** The paper attendance log is the ink-signed dispute record; the chain event is the integrity-bound attestation. Discrepancy between PDF and chain event is a control failure.

## §10.18 CC8.1 and runbook cross-referencing (normative)

**What.** Operational runbooks supporting normative spec requirements MUST cross-reference the spec section number from which the requirement derives. A runbook section describing IKM registration without naming §10.1, multi-region failover without naming §10.15, etc., is a CC8.1 discoverability nit.

**Why this exists.** The chain of evidence runs runbook → spec → design → audit procedure → SOC engagement → examiner workpaper. Without the cross-reference discipline, an examiner can't traverse from a runbook entry back to the normative requirement it supports. §10.18 makes the traversal mechanical.

## What §10.1–§10.18 buys you

The foundational cluster gives you the operational floor every chain-of-custody-adopting institution needs: key custody, HSM discipline, time synchronization, append-only enforcement, RNG quality, constant-time comparisons, multi-region resilience, exit-code conformance, evidentiary-artifact retention, runbook cross-referencing.

Past §10.18, the spec's §10.x sections become more situational — institutions adopt some and not others based on what they do (model handover, GenAI generation, RMA chains, etc.). The foundational cluster is where conformance starts.
